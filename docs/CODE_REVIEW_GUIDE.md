# 代码审查标准与流程（dcache 项目）

> 版本 1.0 ｜ 适用范围：`include/` `src/` `apps/` `tests/` 全部 C++ 代码
> 目标：让「审查意见有统一尺度、合并有明确门槛、质量可被度量」。

---

## 1. 设计原则

1. **审查目标是代码，不是人。** 评论针对具体行，给出「为什么」和「怎么改」。
2. **门槛前置，而不是靠人肉拦。** 格式、告警、静态检查交给工具；人只审工具看不懂的东西（并发语义、缓存正确性、接口契约）。
3. **小 PR 才审得动。** 单次 PR 变更控制在 400 行以内（不含生成代码与测试数据），超过就拆。
4. **一次提完。** 反对挤牙膏式逐轮反馈；一轮审查必须给出该 PR 的全部已知问题。
5. **严重性分级必须显式标注。** 不允许出现「这里最好改一下」这种无法执行的意见。

---

## 2. 角色与职责

| 角色 | 职责 | 不能做什么 |
|---|---|---|
| 作者（Author） | 自测通过、自查清单、写清 PR 意图与风险点、响应审查意见 | 不得自行合并未经审查的 PR |
| 审查者（Reviewer） | 24h 内首响、按分级给意见、对 P0 明确阻断 | 不得只留「LGTM」而无实质检查 |
| 模块维护者（Owner） | `core`（hash/lru/singleflight）、`net`（http_*/peer_pool）、`node`（group/node）三个域的最终裁定 | 不得越过 P0 门槛放行 |

**规则：至少 1 名非作者审查者；涉及 `src/http_server.cpp`、`src/peer_pool.cpp`、`src/lru_cache.tpp`、`src/group.cpp` 的改动，必须由对应模块 Owner 审查。**

---

## 3. 缺陷分级与合并门禁

| 级别 | 定义 | 处理要求 |
|---|---|---|
| 🔴 **P0 Blocker** | 崩溃/数据错误/数据竞争/安全漏洞/接口破坏/关键路径无错误处理 | **必须修复**，PR 不可合并 |
| 🟡 **P1 Suggestion** | 边界未处理、性能隐患、可读性差、缺关键测试 | 本轮修复，或**显式**登记 TODO（含负责人与截止期）后放行 |
| 💭 **P2 Nit** | 命名、注释、风格细节 | 可延后，不得因 Nit 阻塞合并 |

**合并门禁（全部满足才可点 Merge）：**

- [ ] P0 数量 == 0
- [ ] 每条 P1 已修复或已登记 `TODO(owner, date)`
- [ ] CI 全绿（编译 + ctest + ASan/UBSan）
- [ ] 新增/修改逻辑有对应测试，且测试在**不修代码时会失败**（验证测试有效性）
- [ ] 作者已在 PR 描述中写明：「改了什么 / 为什么 / 风险点 / 如何回滚」

## 4. 审查流程（6 步）

```
① 作者自检 ──► ② 提 PR ──► ③ 24h 首响 ──► ④ 分级审查 ──► ⑤ 修复/复评 ──► ⑥ 合并
     │              │              │                │                │
  跑通本地 CI   填 PR 模板      Reviewer 认领    一次性提全量    仅复核改动区
```

**各步要求：**

1. **作者自检**：本地跑 `cmake --build` + `ctest` + Sanitizer；把自查清单勾完再提。
2. **提 PR**：使用 `.github/pull_request_template.md`；标题格式 `[core|net|node] 动词 + 对象`，例：`[net] 修复 HttpServer 关停竞态`。
3. **24h 首响**：审查者必须在 24 小时内给出第一轮意见（可以是「我今天看」）。
4. **分级审查**：按第 5 节清单逐项过；每条意见标注 P0/P1/P2 + 文件:行号 + 原因 + 建议改法。
5. **修复/复评**：作者逐条回复（已改 / 不改并说明理由）；审查者只复核变更区，不做二次全量审查。
6. **合并**：用 Squash 合并，提交信息保留 PR 号。

**时效承诺：** 首响 ≤ 24h；作者修复 ≤ 2 个工作日；P0 热修走「先修后审」，但 24h 内必须补审。

## 5. 审查清单

> 直接作为 PR 描述里的勾选项使用。**带 ★ 的是本项目的高风险区，必须逐条确认。**

### 5.1 正确性

- [ ] ★ **三态语义**：`found / not-found / error` 是否被区分为三种情况？（`GetResult` 目前只有 bool，网络失败会被当成「不存在」并进负缓存）
- [ ] ★ **负缓存（空值缓存）只缓存「确认不存在」**，不缓存超时、连接失败、解析失败、5xx
- [ ] ★ **降级路径**：peer 不可用时是「本机回源」还是「返回缺失」？降级行为是否写进注释与测试？
- [ ] 边界值：容量 0、TTL 0、TTL 极小（<4ms，抖动计算会除零）、空 key、超长 key、含 `/` `%` `"` 的 key
- [ ] 整数运算：`uint64_t` 转 `int64_t`、`ttl` 回绕、`atoi` 溢出
- [ ] 所有 `recv/send/accept/connect/epoll_*` 返回值是否都被检查？`EINTR` 是否重试？

### 5.2 并发安全

- [ ] ★ **共享可变状态是否有明确的所有权注释**（哪个锁保护哪个字段）
- [ ] ★ **读写竞态**：`SetPeers` 重建哈希环时，`PickPeer` 能否读到半更新状态？（当前无同步）
- [ ] ★ **线程生命周期**：`Stop()` 之后是否还有线程可能访问已释放对象？能否安全重启？
- [ ] 锁顺序：是否存在两把锁的交叉获取路径（ABBA 死锁）？
- [ ] 条件变量：`wait` 是否带谓词？唤醒是否遗漏（`notify_one` vs 队列多消费者）？
- [ ] 锁内是否做了阻塞 I/O、DNS 解析、`std::function` 调用？（当前 `SingleFlight` leader 在锁外执行，正确 ✅）

### 5.3 内存与资源

- [ ] **RAII 完整性**：fd、socket、`addrinfo`、线程在所有 return/throw 路径上都被释放？
- [ ] ★ **fd 生命周期**：跨线程交接的 fd，是否存在「关闭后 fd 号被复用、旧事件误伤新连接」？
- [ ] 无界增长：连接表、任务队列、读缓冲、响应体是否都有上限？
- [ ] 移动语义：`std::move` 后是否还使用了源对象？

### 5.4 安全性

- [ ] ★ **内部头不可信任**：`X-DCache-Hops` 等内部语义头是否可能被外部客户端伪造？
- [ ] 输入校验：路径、header、Content-Length、URL 解码结果是否有长度/字符集约束？
- [ ] 慢速攻击：阻塞写是否有超时？单连接能否长期占用 worker？
- [ ] 信息泄露：`/stats` 等运维接口是否对外开放且无鉴权？
- [ ] 格式化：是否全部使用 `snprintf` 而非 `sprintf`？
- [ ] ★ **传输层**：节点间是否加密？token 是否以明文过网？客户端是否**强制**校验证书
      （包括 IP 字面量走 `set1_ip_asc` 而不是 `set1_host`）？

### 5.5 性能

- [ ] 热路径是否有不必要的拷贝（`std::string` 按值返回、`std::map` 代替 `unordered_map`、每请求 `getaddrinfo`）？
- [ ] 锁粒度：是否在锁内做了 `std::string` 拷贝等重操作？（`LruCache::get` 返回 `optional<V>` 是在锁内拷贝）
- [ ] 是否有连接池/复用？每请求新建 TCP 的代价是否可接受？
- [ ] **工作线程里有没有可能阻塞的 socket I/O？** 只要有，并发度就由对端行为决定
      （对端不读，`send()` 就停住）。写响应应当在事件循环里非阻塞完成。
- [ ] 异常路径是否比正常路径更贵（`exception_ptr` 传递成本）？

### 5.6 可维护性

- [ ] 命名是否表达意图（`r`、`t`、`g` 这类单字母只在 3 行内使用）
- [ ] 注释解释**为什么**，而不是复述代码；非显然的取舍必须写理由
- [ ] 魔法数字是否集中（`kMaxForwardHops`、`2000ms`、`64KB`、`4 workers`、`30000ms`）
- [ ] 头文件依赖是否最小？`#include "../src/xxx.tpp"` 这类跨目录引用是否可接受？
- [ ] 公开 API 是否必要？（`Group::Get(key, hops)` 暴露内部跳数给外部调用方）

### 5.7 测试

- [ ] 新增分支是否都有用例？失败路径（超时、500、半包、连接重置）是否覆盖？
- [ ] 并发用例是否有「栅栏 + 慢函数」构造竞争窗口，而不是靠 sleep 撞运气？
- [ ] 断言是否检查了**行为**而非实现细节？
- [ ] 是否考虑加入 TSan 任务（并发代码必须有）
- [ ] 新增的解析逻辑是否在 fuzz 覆盖范围内（`fuzz/` 三目标必须跟着改，否则新分支等于没测）

### 5.8 文档

- [ ] 公开接口的语义（尤其是错误语义）是否在头文件注释中说明？
- [ ] 行为变更是否同步 `README.md` / `docs/`？

CI 拆成 6 个 job：`build-and-test` / `sanitizers`（ASan+UBSan） / `tsan` / `lint` / `coverage` / `fuzz`。

**构建命令只写一份。** 六个 job 都调用 `scripts/ci.sh <build|asan|tsan|lint|coverage|fuzz>`，CI 配置里只声明「在哪个 runner 上跑哪一项」。这样换平台（GitHub Actions → Gitee Go / Jenkins / 云效）时改的是平台方言，构建逻辑不动，也不会出现「一边加了 Sanitizer、另一边忘了」的漂移。

### 6.1 覆盖率门禁是怎么设计的（以及三个坑）

`-DDCACHE_COVERAGE=ON` 打开 `--coverage -O0 -g`，`gcovr --fail-under-line` 卡 75%。
首跑实测 **79%**；加入 TLS 后是 2136/1674（78%），加入证书热加载后回到 2165/1723（**79%**），
加入慢客户端隔离后是 2242/1771（仍是 **79%**——新增的 77 行被用例走全了）。地板值取 75：
留 3 个点给工具版本差异（`gcovr`/`gcc` 的计数口径会小幅漂移），
超过这个余量的下跌只可能是真的少测了。再往上抬按「实测 − 3」逐步收紧。

设计上有三个刻意的选择：

1. **只统计 `src/` 与 `include/`，排除 `tests/` 与 `apps/`。** 用测试文件给测试打分没有意义；
   `apps/` 是入口，靠手工跑，覆盖率天然低，混进来只会稀释信号。
2. **必须单判一次「报告为空」。** `gcovr` 在「一个文件都没匹配到」时不报错，输出一张
   0/0 的空表——**看起来和 100% 一样漂亮**，`--fail-under-line` 也可能直接放行。
   这和第十一节那条「恒真断言」是同一类错误：门禁看起来在拦，实际什么都没拦。
3. **数字要能被机器取走。** job 日志需要仓库 admin 权限，job summary 只能人眼看。
   所以 workflow 额外把 `TOTAL` 行打成一条 **annotation**（`::notice::`），
   它能用匿名 API 读到：
   `GET /repos/{owner}/{repo}/check-runs/{id}/annotations`。

还有一条不能踩：**覆盖率和 Sanitizer 不要一起开**。Sanitizer 下进程异常退出会丢掉
`.gcda`，覆盖率会莫名偏低，这类「工具互相干扰」的假信号最难查。

### 6.2 模糊测试：fuzz 的价值全在断言上

覆盖率门禁回答的是「该跑的都跑了吗」，回答不了「喂垃圾会怎样」。三个手写解析器
（`json` / `url` / HTTP 请求行）是全项目**唯一直接吞不可信外部字节**的地方，
其余模块吃的是自己进程内的数据——所以 fuzz 目标只挑这三个，不是图省事。

四个刻意的选择：

1. **解析器必须能被单独调用。** `ParseRequest` 原本藏在 `http_server.cpp` 的匿名命名空间里，
   想测它只能起一个真 socket；而「声明体超过 64KB」这种分支，集成测试**根本发不出去**
   （服务端在读缓冲超限时就把连接关了，压根走不到解析）。所以先把它拆成
   `src/http_parser.cpp`，再用 `tests/test_http_parser.cpp` 直调 10 条边界。
   **可测性是设计属性，不是事后补的。**
2. **库必须一起插桩**（`-fsanitize=fuzzer-no-link`）。只给 fuzz 目标插桩、库不插的话，
   fuzzer 看不到任何「哪些分支走到过」的信息，退化成纯随机字节生成器——
   跑十分钟的随机测试未必比手写用例强。
3. **断言检查的是不变式，不是「别崩」。** 只求不崩的话，一个返回垃圾结果但不越界的解析器
   会被判为「通过」。这里断的是行为：编码后必须能原样解码回来（往返一致）、
   同一段字节解析两次结论必须相同（幂等）、请求收到一半时只能回答「还要更多」（前缀性质）。
   最后一条尤其重要——半包是 TCP 的常态，破坏了它，服务端会在半包到达时直接丢请求。
4. **CI 只跑 30 秒**（`FUZZ_SECONDS`）。CI 挡的是「几秒就能撞出来」的崩；
   深度 fuzz 是本地或夜间任务的事，把它塞进每次提交只会让反馈变慢。

**第一轮就撞出了什么。** `fuzz_json` 启动 30 秒内就撞破了往返不变式：`src/json.cpp` 的字段扫描
用 `body.find("\"found\"")` 直接搜，不认字符串边界，命中可能落在**值内部**——缓存值是 `a"found`
时编码结果里的 `a\"found"` 恰好含 `"found"`，于是要么把正常响应判成畸形（→ 503），
要么在值构造得巧时把「命中」读成「未命中」（→ 缓存退化成直连）。**这不是崩溃，是语义反了**，
所以 ASan、TSan、四批 review 全都没看见。修法见报告第十三节。

这条最值得记住的不是那个 bug，而是：**人工 review 会替代码脑补「这里应该是字段名」，fuzzer 不会。**

另外两个工程细节：

- **语料放在构建目录里跑**，不直接写 `fuzz/corpus/`。libFuzzer 会持续往「第一个语料目录」写新样本，
  指向源码树的话，每次本地跑完都多出一堆未跟踪文件，很快就会有人把整个语料目录删掉。
- **`fuzz/corpus/http_request/*` 在 `.gitattributes` 里标了 `-text`。** 仓库默认 `* text=auto eol=lf`，
  不豁免的话每次检出都会把 CRLF 改成 LF —— 种子本身就不是合法请求了，
  fuzzer 等于从一堆废样本起步。

> 结论写进注解，和覆盖率那节同理：`::notice::` / `::error::` 带 `cov:` `ft:` 或崩溃原因，
> 不需要 admin 权限就能取到。只写「通过」而不说跑了多少次、覆盖多少边，和「配了没跑」没有区别。

**平台选择要注意的一点：** 本仓库主仓在 Gitee，但 `.github/workflows/ci.yml` 是 GitHub Actions 的格式，**Gitee 不会执行它**。Gitee Go 挂在企业版下（可免费开通企业试用），且执行自定义脚本的 `shell@agent` 步骤需要自备 Linux 主机接入主机组 —— 个人仓库指望「云端免费跑 ctest」是走不通的。因此 CI 实际生效需要满足其一：

- 推到 GitHub（公开仓库 Actions 免费），或
- 在 Gitee 侧接一个能拉仓库的外部流水线（云效 / Jenkins，需自备执行节点）。

在 CI 真正跑起来之前，**不要把「CI 全绿」当作已达成**，本地 `bash scripts/ci.sh all` 是同一份逻辑，可以先跑。

### 6.3 TLS 不是「加个开关」，是四处所有权和时序的改动

`-DDCACHE_TLS=ON` 之后节点间走 TLS。这一节记录**重做时不要再踩**的东西：

1. **OpenSSL 类型不许进头文件。** `http_server.hpp` 里出现 `SSL_CTX*`，`DCACHE_TLS=OFF`
   的构建就得在事件循环、连接结构体、写响应分支里各套一层 `#ifdef`。用一个
   `include/tls.hpp`（pimpl 句柄 + 两个枚举）+ 两个实现文件（`tls_openssl.cpp` /
   `tls_stub.cpp`）把条件编译挡在库外面。
2. **缺 OpenSSL 就 configure 失败，不许静默降级成明文。** 静默降级会让「已启用 TLS」
   这个结论在别人机器上不成立，而这种事只有出事之后才会被发现。
3. **握手必须非阻塞，且每次推进都要收敛 epoll 关注事件。** `EPOLLOUT` 是水平触发的：
   注册了不放，`epoll_wait` 每轮立刻返回，直接 100% CPU 空转。
4. **`SSL_pending` 会丢事件。** 握手完成时应用数据可能已经在 SSL 内部缓冲里，
   而 socket 早被读空——epoll 不会再触发 `EPOLLIN`。所以握手推完必须接着读一次。
5. **`SSL*` 跟着 fd 跨线程。** `Task` / `Recycled` / `Conn` 三处都要带，用 `unique_ptr`
   表达所有权，`conns_.erase()` 顺带释放。手写 `SSL_free` 迟早漏一次。
6. **写失败即不可恢复。** 半个 TLS 记录写出去之后这条会话就废了，绝不能因为
   「客户端要 keep-alive」而把连接塞回池子。

测试侧的规矩同样重要：**反向用例必须存在且能红**。`test_tls` 里 3 组用例断言的是
「必须失败」（错误的 CA / 明文打 TLS 口 / 证书没有对应 IP SAN），
并用一次实际提交（把 `VERIFY_PEER` 改成 `VERIFY_NONE`）验证过它们真的会红。

### 6.4 热加载的坑不在「怎么换」，在「换完谁还活着」

1. **`SSL_CTX` 自带引用计数，这就是全部前提。** `SSL_new` 加一次引用、`SSL_free` 减一次，
   所以替换自己持有的那份只是减引用，在途会话不受影响。`shared_ptr` 是为了**免锁**
   （让 `ReloadTls` 任意线程可调），不是为了让上下文能被共享——这两件事容易混。
2. **先建后换，失败一个字节都不动。** 「失败不影响服务」靠顺序保证，不靠失败分支里修复。
   运维覆盖 PEM 时读到半截文件是常态（`cp` 非原子，`mv` 才是）。
3. **信号处理器里只能置 `volatile sig_atomic_t`。** 读 PEM 要 malloc、锁、`std::string`，
   全不是 async-signal-safe。
4. **`SSL_write` 没有 `MSG_NOSIGNAL`。** 明文路径的 `send_all` 都有，TLS 路径绕开了它们，
   于是「写到已关闭连接」会变成 SIGPIPE → 进程退出。这是 DoS，不是小毛病。
5. **TLS 1.3 下服务端看不到客户端的证书校验失败。** 服务端 `SSL_accept` 发完 Finished
   就返回成功（1-RTT）。所以别写「错误的 CA 必须让服务端记一次握手失败」这种断言——
   它是靠时序通过的假断言，换个优化级别就红。

第 4、5 条的共同点：**缺陷藏在两条路径的差异里**，而所有工具检查的都是单条路径。

### 6.5 慢客户端隔离：把「不会拖累别人」写成断言

1. **工作线程里做 socket 写，等于把并发度交给对端决定。** 对端不读，`send()` 就会停在
   发送缓冲区满的那一刻，一个 worker 被按死；`SO_SNDTIMEO` 只是给这次按住加了个上限
   （本项目是 2 秒）。判断标准很简单：**这个阻塞点等的东西，是不是外部可控的？**
2. **给共享的事件位加第二个使用者时，分流依据要从「事件」换成「状态」。**
   `EPOLLOUT` 原本只服务于 TLS 握手，写回也要用之后，若仍按「`EPOLLOUT` 就走写回」分流，
   「握手需要回写」就会被误送进写回逻辑，握手永远推不完（等 10 秒空闲回收才断）。
   正确做法是一律进 `handle_read`，由它按连接的阶段分流。
3. **非阻塞 TLS 写必须开两个 mode。** `SSL_MODE_ENABLE_PARTIAL_WRITE`（否则 8MB 响应
   要么全写完要么 `WANT_WRITE`，剩余部分全靠 OpenSSL 内部缓存，缓存多少由对端读速决定）；
   `SSL_MODE_ACCEPT_MOVING_WRITE_BUFFER`（否则 `WANT_WRITE` 后带新偏移量重试 =
   `bad write retry`，连接当场断）。后者的可怕之处是**所有小响应测试都是绿的**。
4. **一次 flush 要让出事件循环。** 写是 memcpy，但事件循环是单线程的；一条 8MB 响应
   一口气推完，这一轮里别人的响应就被推迟了。给个上限（本项目 256KB），
   多花的只是一次 `epoll_wait` 往返。能这么干的前提是 `EPOLLOUT` 水平触发。
5. **超时判据要把「总时长」换成「停滞时长」。** 一旦没有任何一次调用会等，
   `SO_SNDTIMEO` 那套就失效了；判据必须变成「距离上次写出有进展过了多久」，
   否则给慢客户端正常吐大响应的连接会被误杀。
6. **缓冲要真的还回去。** 写完 keep-alive 响应用 `std::string().swap(out)`，
   不能只 `clear()`——后者保留容量，一条连接就会一直挂着上次那个 8MB。
7. **先让断言红。** 这一批的唯一正确做法是先只提交测试（`a62ffc8`），确认 CI 红在
   `!resp.empty()`，再动实现。红线证明两件事：缺陷存在，断言不恒真。
   如果「改好了」只能靠「感觉快了」描述，那就还没到能改的时候。
8. **换来的新代价要写出来。** 改完之后，写不动的连接会**持有整条响应在内存里**，
   于是内存上界从「连接数 × 读缓冲」变成「连接数 × 响应体」。这不是退化
   （改之前那条响应也在内存里，还额外占一个 worker），但它是新的事实，必须进文档。

## 7. 评分卡（用于季度健康度评估）

每个维度 0–100 分，按权重加权。评分锚点：

- **90–100**：有防护性设计 + 失败路径测试，新人可直接复用
- **75–89**：正常路径正确，边界有少量遗漏
- **60–74**：能用，但在异常/并发/攻击场景下会出问题
- **40–59**：存在会导致数据错误或崩溃的缺陷
- **0–39**：不可用

| 维度 | 权重 | 评分要点 |
|---|---|---|
| 正确性 | 25% | 语义完整性、边界、错误分类 |
| 并发安全 | 20% | 数据竞争、线程生命周期、锁设计 |
| 安全性 | 15% | 输入校验、内部接口信任边界、DoS 面 |
| 可维护性 | 15% | 分层、命名、注释质量、API 收敛 |
| 测试 | 12% | 覆盖广度、失败路径、并发用例质量 |
| 工程化 | 8% | CI、静态检查、构建可复现 |
| 文档 | 5% | README、设计说明、接口契约 |

**评级：** A（≥90）可作团队参考实现 ｜ B（80–89）可上线 ｜ **C（60–79）可演示，不可直接上线** ｜ D（<60）需重构。
